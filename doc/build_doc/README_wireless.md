# 无线模块移植说明

本文档面向需要将无线模块移植到其他 MCU 或其他工程的开发者。目标是先明确无线模块依赖哪些硬件、哪些代码必须改、哪些空口协议不能随意改。

> 当前实现不是通用无线库，而是“STC32G + LT8920 + KCT8206L + 项目业务协议”的工程实现。更换 MCU 时，不要只改几个 GPIO 宏，需要先拆清楚平台适配层、LT8920 驱动层和业务协议层。

## 移植前必须确认

1. 新板子是单颗 LT8920 还是双颗 LT8920。
2. SPI 使用 GPIO 模拟还是 MCU 硬件 SPI。
3. 是否保留当前调度周期。
4. 是否需要兼容现有遥控器或对端设备空口协议。
5. 配对信道、工作信道、同步字和包格式是否保持不变。
6. 当前业务层是否仍直接控制电机、LED、GPS 或自动驾驶状态。

如果只是更换 MCU 且仍兼容原对端，建议优先保持 LT8920 寄存器配置、信道算法、同步字和业务帧格式不变，只替换 GPIO/SPI/延时/日志等平台接口。

当前说明边界：

- 本文重点面向“移植到其他 MCU/工程”，不是当前根目录无线模块的主维护入口。
- 当前根目录真实运行关系请优先看 `Code_boweny/Device/WIRELESS/README.md` 和根目录 `README.md`。
- 当前电机控制已经下沉到 `ShipControl`，不要再按旧思路把无线业务层写成直接控电机。

## 建议代码分层

| 层级 | 建议文件 | 内容 |
|------|----------|------|
| 平台层 | `wireless_port.*` | GPIO、SPI、延时、日志、临界区 |
| 芯片层 | `lt8920.*` | 寄存器、FIFO、收发模式 |
| 协议层 | `wireless_protocol.*` 或 `ship_protocol.*` | 配对、信道、同步字、帧编解码 |
| 业务层 | `wireless_app.*` | 电机、LED、GPS、自动驾驶接口 |

移植时应优先把平台相关内容收口到 `wireless_port.*`，避免驱动和协议代码到处直接操作 MCU 专用端口。

## 平台层需要提供的能力

| 能力 | 移植要求 |
|------|----------|
| GPIO 输出 | 控制 CS、RST、ANT_SEL、RXEN、TXEN |
| SPI 收发 | 提供单字节同步收发接口 |
| 延时 | 提供 us/ms 延时 |
| 日志 | 可接工程日志，也可临时置空 |
| 基础类型 | 明确 `u8/u16/u32/s8/int16` 等类型 |
| 调度 | 提供等效的主循环或定时任务入口 |

推荐抽象：

```c
WIRELESS_CS_WRITE(level)
WIRELESS_RST_WRITE(level)
WIRELESS_ANT_SEL_WRITE(level)
WIRELESS_RXEN_WRITE(level)
WIRELESS_TXEN_WRITE(level)
WIRELESS_SPI_TRANSFER(byte)
WIRELESS_DELAY_US(us)
WIRELESS_DELAY_MS(ms)
WIRELESS_LOG(...)
```

## 当前 STC32G 接线

| 信号 | 当前引脚 | 说明 |
|------|----------|------|
| `SPI_CLK` | `P3.2` | SPI4 SCLK |
| `MISO` | `P3.3` | SPI4 MISO |
| `MOSI` | `P3.4` | SPI4 MOSI |
| `SPI_SS` | `P3.5` | 手动片选 CS |
| `RST` | `P5.0` | LT8920 复位 |
| `ANT_SEL` | `P5.1` | 天线选择 |
| `RXEN` | `P1.3` | KCT8206L 接收通道使能 |
| `TXEN` | `P5.4` | KCT8206L 发送通道使能 |

当前工程使用硬件 SPI 方向接入，不建议再新增软件 SPI，除非后续实测发现 LT8920 时序必须由 GPIO 精确控制。

## LT8920 关键配置

| 项目 | 当前值 / 位置 | 移植说明 |
|------|---------------|----------|
| 射频芯片 | LT8920 | 对端不变时不要随意更换寄存器配置 |
| 发射功率 | `RF_Power = LT89xx_6dBm` | 定义在 `lt8920.h` |
| 配对信道 | `Pair_Channel = 0x7F` | 需结合实测确认 |
| 同步字 | `SyncPairWord` / `SyncTransferWord` | 对端兼容时必须保持一致 |
| CRC | 开启 | 寄存器配置中启用 |
| 包长度 | FIFO 包内带长度 | 业务帧仍有自己的长度字段 |

`RF_Encrypt_Config()` 这类旧命名容易误解。当前相关逻辑主要配置的是 LT8920 Sync Word，不是真正的数据加密。新代码中建议命名为 `LT8920_SetSyncWord()`。

## 空口协议

当前应用层帧以 `0xAA` 开始、以 `0xBB` 结束，中间包含长度、命令字和 payload。具体格式以 `ship_protocol.c` 的组包和解包代码为准。

在线口径必须分开：

- 上位机“遥控链路显示在线”按完整 `0xAA ... 0xBB` 头尾包活动刷新，不要求必须收到 `0x11`。
- 固件业务分发仍必须通过长度、命令字、payload 和 XOR 校验。
- 固件电机安全保活只认有效 `0x11` 控制帧；显示在线不等于控制帧保活。

常见命令：

| 命令 | 含义 | 方向 |
|------|------|------|
| `0x0F` | 配对响应 | 对端到船端 |
| `0x10` | 配对请求 | 船端到对端 |
| `0x11` | 控制命令 | 对端到船端 |
| `0x12` | GPS / 状态上报 | 船端到对端 |

若对端固件不改，命令字、字段顺序、字段长度和大小端都必须保持一致。

## 推荐移植步骤

1. 拆出平台接口，确保 LT8920 驱动不直接包含 MCU 专用头文件。
2. 只验证 LT8920 层：复位、寄存器写入、寄存器回读、FIFO 固定包收发。
3. 接入配对流程：确认配对包能发出、对端能响应、工作信道和同步字能派生。
4. 接入业务命令：验证 `0x11` 控制命令和 `0x12` 状态上报。
5. 最后再接电机、GPS、自动驾驶等业务动作，避免底层未稳定时被业务逻辑干扰。

## 单颗 LT8920 特别说明

单颗 LT8920 是半双工模型，必须明确什么时候发、什么时候收、发多久、收多久。建议状态机：

| 状态 | 行为 |
|------|------|
| `PAIR_TX` | 周期发送配对请求 |
| `PAIR_RX` | 切到接收等待配对响应 |
| `WORK_RX` | 主要时间保持接收遥控命令 |
| `WORK_TX_STATUS` | 短时间发送 GPS / 状态包 |
| `WORK_RETURN_RX` | 发送完成后立即回到接收 |

需要重新评估 GPS/状态包上报频率、遥控失联超时阈值和对端是否支持这种收发时序。

## 调试建议

优先顺序：

1. 调硬件链路：RST、SCK、MOSI、MISO、CS、电源、晶振、天线。
2. 调 LT8920 状态：初始化结果、关键寄存器、当前信道、同步字、状态寄存器、FIFO 长度。
3. 调业务协议：配对 seed、派生信道、同步字、命令字、payload 长度、失联计数。

如果现象是偶尔能配对但长期不稳定，优先检查 SPI 时序、调度周期、电源和天线，不要先怀疑业务解析。

## 移植验收清单

- 新 MCU 上不再直接依赖旧平台专用头文件。
- GPIO / SPI / delay / log 已集中到平台适配层。
- LT8920 寄存器能稳定写入和回读。
- 能稳定完成配对。
- 能切换到工作信道。
- 能稳定接收 `0x11` 控制命令。
- 能周期发送 `0x12` GPS / 状态包。
- 连续运行不会出现 SPI 偶发读写错误或状态机卡死。
